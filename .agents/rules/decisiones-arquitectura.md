# Decisiones de arquitectura

1. **Backend como monolito modular en Next.js Route Handlers** (`app/api/**` por dominios) en vez de un servicio aparte (NestJS/Express): un solo deploy en Vercel, comparte tipos y validadores Zod con el frontend, y el tamaño del proyecto no justifica infraestructura separada.
2. **Estructura feature-based con route groups**: `app/(shop)`, `app/(auth)`, `app/(account)`, `app/admin`, `app/api`. Separación estricta: `lib/` = lógica de negocio/servicios, `app/api/` = controladores, `components/` = UI pura, `page.tsx` = composición.
3. **Base UI en lugar de Radix**: shadcn v4 migró upstream; forzar Radix implicaría fijar registry antiguo. Se mantiene Base UI (mismo equipo, misma a11y).
4. **Vercel Blob para imágenes** (vs Cloudinary): setup local más simple y misma plataforma de deploy.
5. **Redis local vía Docker en dev, Upstash en producción**: el cliente se conecta por `REDIS_URL`, intercambiable.
6. **Tailwind v4 con tokens CSS** (`@theme` en `globals.css`) en vez de `tailwind.config`: es el estándar de Tailwind 4 y shadcn v4.
7. **Prisma + PostgreSQL** (Fase 1): relacional por integridad de pedidos/stock; Neon en producción.
8. **Dinero siempre en centavos enteros** (`priceCents`, `totalCents`…): compatible con Stripe y sin errores de redondeo de flotantes. Convención obligatoria (ver `.agents/rules/convenciones.md`).
9. **Sesiones JWT (no database sessions)** con config de Auth.js dividida: `lib/auth/auth.config.ts` es edge-safe (sin Prisma/bcrypt) y la usa el middleware; `lib/auth/index.ts` añade adapter y providers para el runtime Node. El rol viaja en el token (callbacks `jwt`/`session`) y se re-verifica en servidor.
10. **Pedidos con snapshot**: `Order`/`OrderItem` copian nombre, SKU, precio y dirección al momento de compra; las FK a catálogo son `SetNull` para que el historial sobreviva a borrados de productos.
11. **Las páginas llaman a los servicios de `lib/` directamente** (Server Components), no a su propia API HTTP; `app/api/**` queda para consumo desde el cliente (y futuros consumidores externos). Los filtros del PLP viven en la URL: los controles cliente solo hacen `router.push` con nuevos search params y el servidor re-renderiza — el grid en sí es RSC. ISR: Home y PDP con `revalidate = 300`; PLP y búsqueda dinámicas (dependen de searchParams) con streaming/Suspense.
12. **Checkout activo: manual vía WhatsApp; Stripe construido pero dormido** (`NEXT_PUBLIC_CHECKOUT_MODE`, default `"whatsapp"`). El código de Stripe (checkout hosted + webhooks) está **intacto y verificado** — reactivarlo es poner las claves en `.env` y `NEXT_PUBLIC_CHECKOUT_MODE="stripe"`. En modo whatsapp: `/checkout` recoge contacto+envío, `POST /api/checkout/manual` crea la orden `PENDING_PAYMENT`, el operador confirma el pago desde el admin (`→ Pagado`) o cancela (restaura stock); pedidos sin confirmar expiran a las `ORDER_PAYMENT_EXPIRY_HOURS` (48 por defecto) vía barrido idempotente (se ejecuta al cargar las vistas admin de pedidos y/o cron).
13. **Concurrencia de stock: UPDATE condicional atómico** (`lib/inventory/stock.ts`). La reserva usa `updateMany({ where: { id, stock: { gte: qty } }, data: { decrement } })` dentro de `$transaction`: Postgres bloquea la fila durante el UPDATE, chequeo y decremento son la misma sentencia, así que dos pedidos concurrentes por la última unidad nunca sobrevenden — el perdedor recibe `INSUFFICIENT_STOCK` (409) y su transacción entera se revierte. Se eligió sobre `SELECT ... FOR UPDATE` por ser más simple e igual de correcto para este modelo (no hay lecturas intermedias que proteger). Cubierto por test de integración real contra Postgres.
14. **Semántica de estados vs stock:** `PENDING` (Stripe) NO reserva stock (se decrementa al pagar, vía webhook); `PENDING_PAYMENT` (WhatsApp) SÍ reserva al crear. Cancelar órdenes con stock retenido (`PENDING_PAYMENT`/`PAID`/`SHIPPED`/`DELIVERED`) lo restaura; los reembolsos NO (la mercancía puede estar con el cliente). `EXPIRED` solo lo pone el barrido, nunca el admin.
15. **Flujo de pago Stripe: orden primero, stock al pagar.** El checkout crea la Order PENDING (con snapshot de precios/SKU desde la DB) antes de la sesión de Stripe (`metadata.orderId` la enlaza); el stock se valida al iniciar el checkout pero solo se decrementa cuando el webhook confirma el pago, en transacción idempotente (orden no-PENDING = ya procesada, retries de Stripe seguros). Ventana de sobreventa entre validación y pago aceptada y documentada: el decremento condicional loggea underflow para revisión manual en vez de bloquear un pago ya cobrado. Checkout de invitados permitido: el email definitivo llega del webhook (`customer_details`).
16. **Cuenta: recursos siempre scoped por `userId` en el servicio** (`where: { id, userId }`); un recurso ajeno responde 404 (no 403, para no revelar existencia). Guard de rutas API con `requireUser()` (401); páginas con `auth()` + `redirect` además del middleware.
17. **Fuentes self-hosted** (`next/font/local` + woff2 variable en `app/fonts/`, subset latin) en vez de `next/font/google`: la descarga de Google Fonts en build-time colgaba el build tras limpiar caché con la red de WSL rota por el VPN (ver troubleshooting). Sin dependencia de red en build, mejor privacidad, mismo resultado visual.
18. **Estados de pedido como máquina de transiciones** (`lib/admin/order-status.ts`): el admin solo puede aplicar transiciones del mapa `ALLOWED_TRANSITIONS`; `PAID` lo pone únicamente el webhook de Stripe; CANCELLED/REFUNDED son terminales. Transición inválida → 409.
19. **Búsqueda: Postgres filtra, Meilisearch busca.** `/api/products` (PLP con filtros exactos) va directo a Prisma; `/api/search` (texto libre + typo-tolerance) va a Meilisearch con documentos desnormalizados. Los filtros de Meili se construyen escapando valores con `JSON.stringify` (previene inyección en la sintaxis de filtro). El browser solo recibe la search key pública scoped al índice `products`; la master key nunca sale del servidor. Sync del índice manual por ahora (`npm run search:sync`), idempotente.
20. **Endurecimiento de seguridad sin librerías nuevas (2026-11-19).** Tras una auditoría: confirmación de pedido accesible solo por su dueño (cookie httpOnly `order_<id>` o sesión), tope anti-abuso de 3 pedidos `PENDING_PAYMENT` por teléfono/hora (429) y `MAX_QUANTITY_PER_LINE = 10`, `safeCallbackUrl` contra open redirect, JWT de 8 h y rol releído de la DB en los guards de admin, login con hash dummy (sin enumeración por tiempo), cabeceras de seguridad en `next.config.ts`, JSON-LD escapado, subidas a Blob con nombre aleatorio, logs sin datos personales. Rate limiting por IP de login/registro: se delega a una regla del Vercel Firewall (sin código).
21. **Cron de expiración diario** (`vercel.json`, `0 6 * * *`): el plan Hobby de Vercel solo permite crons diarios; el barrido igual corre al abrir las vistas de pedidos del admin, así que la expiración no depende solo del cron.
